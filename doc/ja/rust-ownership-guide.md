# 第1章 イントロダクション:なぜ所有権なのか

## 1.1 メモリ管理の3方式

プログラムが動的に確保したメモリを「いつ、誰が解放するか」。この問いへの答えは、歴史的に3つの流派に分かれてきました。

| 方式 | 代表言語 | 解放のタイミング | 主なリスク |
|---|---|---|---|
| **手動管理** | C, C++(生ポインタ) | プログラマが明示的に指示 | 解放忘れ(リーク)、二重解放、解放後使用(use-after-free) |
| **ガベージコレクション(GC)** | Java, Go, C#, Python | ランタイムが「もう使われない」と判定した後、いつか | 停止時間(pause)、メモリフットプリント増、解放タイミングの非決定性 |
| **所有権(コンパイル時管理)** | Rust | **コンパイル時に決定された地点**で自動解放 | 学習コスト、コンパイラとの「格闘」 |

手動管理は最速・最軽量ですが、人間の注意力に安全性を依存します。C/C++で報告される重大な脆弱性の大半がメモリ安全性の問題に起因することは、Microsoft や Google のセキュリティチームが繰り返し報告してきた通りです。

GCはこの問題を「解放の判断をランタイムに委譲する」ことで解決しました。Javaエンジニアである読者は、この恩恵を四半世紀にわたって享受してきたはずです。`new`したら後は忘れてよい。ダングリングポインタは原理的に存在しない。これは偉大な発明です。

Rustの所有権システムは、第3の道です。**「どの値がいつ不要になるかを、型システムの規則としてコンパイル時に決定する」**。ランタイムのGCは存在せず、解放コードはコンパイラが決定的な位置に挿入します。つまり、

- 手動管理と同等の実行時性能・予測可能性
- GCと同等(以上)の安全性

の両立を狙った仕組みです。ただし無料ではありません。代償は「コンパイル時にコンパイラを納得させる」という新しい種類の作業であり、本書はまさにその作業を体系的に学ぶためのものです。

## 1.2 GCとのトレードオフ

「GCで十分ではないか?」——これは正当な問いです。実際、多くのアプリケーションではGCで十分です。所有権が優位に立つのは、以下の性質が要求される場面です。

### (1) 停止時間と予測可能性

JavaのGCは大きく進化しました(G1、ZGC、Shenandoah)。ZGCならサブミリ秒の停止時間を実現します。それでも「GCがいつ走るか」はアプリケーションコードからは制御できず、レイテンシのテール(p99.9など)に非決定性が残ります。Rustでは、解放はスコープを抜けた瞬間に決定的に発生します。「この関数のこの行で解放される」とソースコードから読み取れます。

### (2) メモリフットプリント

GCは効率よく動くために「余裕」を必要とします。ヒープサイズを実使用量ギリギリに絞るとGC頻度が跳ね上がるため、実務では実使用量の数倍のヒープを与えるのが定石です。Rustは必要な分だけを必要な間だけ保持するため、コンテナ環境や組み込み機器のようにメモリが課金・制約対象になる環境で効きます。

### (3) 解放されるのはメモリだけではない

Javaで`finalize()`が非推奨になり、`try-with-resources`が導入された経緯を思い出してください。GCが管理するのは**メモリだけ**であり、ファイルハンドル・ソケット・ロックといったリソースの解放タイミングは保証されません。Rustの所有権は「値の破棄」を一般化した仕組みなので、**あらゆるリソースがメモリと同じ規則で決定的に解放されます**(第3章のDropで詳述)。

### (4) データ競合の静的排除

これは意外に思われるかもしれませんが、所有権システムの最大の恩恵はメモリ管理ではなく**並行処理**に現れます。「可変な状態を複数のスレッドが同時に触る」ことをコンパイル時に禁止できるのです(第8章)。JavaのGCはメモリ安全を保証しますが、データ競合(data race)は防ぎません。

### 一方、GCが優位な点

公平のために書きます。以下の点ではGC言語のほうが楽です。

- **循環参照を含む複雑なオブジェクトグラフ**:GCは到達可能性で判定するため循環を自然に回収します。Rustの参照カウント(`Rc`)は循環をリークします(第6章)。
- **開発速度**:所有権を考えずに書けるぶん、プロトタイピングは速い。
- **既存資産と人材**:これは技術ではなく現実の話ですが、無視できません。

**Rustは「GCより優れている」のではなく「異なるトレードオフを選んでいる」**。この認識が、以降の章で規則の意図を理解する土台になります。

## 1.3 所有権が保証すること・しないこと

過大評価も過小評価も学習の妨げになるので、最初に境界線を引いておきます。

**保証すること(safe Rustの範囲で)**

- 解放後使用(use-after-free)が起きない
- 二重解放が起きない
- ダングリング参照が存在しない
- nullポインタ参照が存在しない(そもそも`null`がない)
- データ競合(複数スレッドによる非同期な読み書きの衝突)が起きない
- バッファオーバーラン(境界外アクセス)が起きない(実行時検査を含む)

**保証しないこと**

- **メモリリークの完全排除**:`Rc`の循環参照や`std::mem::forget`により、safe Rustでもリークは可能です。リークはメモリ「安全性」の問題(不正なメモリを読む)とは区別され、Rustは前者のみを保証対象とします。
- **デッドロックの防止**:ロックの取得順序ミスによるデッドロックは普通に書けます。
- **レースコンディション一般の防止**:データ競合は防ぎますが、「チェックしてから使うまでの間に状態が変わる」ような論理的競合(TOCTOU)は防げません(第8章で詳述)。
- **論理バグの防止**:当然ながら、仕様の誤解はコンパイラには見えません。
- **パニック(実行時異常終了)の排除**:配列の境界外アクセスや`RefCell`の借用違反は、未定義動作ではなくパニックという「安全な失敗」になります。安全 ≠ 落ちない、です。

## 1.4 Javaエンジニアが持ち込むと危険な前提の一覧

本書全体の「予告編」です。Javaで身体に染みついた以下の前提は、Rustでは**すべて成り立ちません**。各項目がどの章で覆されるかを示します。

| Javaでの常識 | Rustでの現実 | 詳述 |
|---|---|---|
| オブジェクトはヒープに置かれ、変数は参照である | 変数は**値そのもの**を持つ。ヒープに置くかどうかは型と書き方で決まる | 第2章 |
| 代入(`b = a`)は参照のコピーで、両方の変数から使える | 代入は多くの型で**ムーブ**であり、元の変数は使用不能になる | 第3章 |
| 変数はデフォルトで再代入可能(`final`は例外的) | 変数はデフォルトで**不変**(`mut`が例外的) | 第3章 |
| 参照はいくつでも作れて、いつでも書き換えられる | **共有(複数`&`)と可変(単一`&mut`)は排他** | 第4章 |
| `null`で「値がない」を表す | `null`は存在しない。`Option<T>`で型として表現する | 第11章 |
| リソース解放は`try-with-resources`で明示する | すべての値が自動的に「try-with-resources相当」 | 第3章 |
| イテレーション中のコレクション変更は実行時例外(`ConcurrentModificationException`) | **コンパイルエラー**として静的に検出される | 第4章 |
| スレッド安全性はドキュメントと規約で守る(「このクラスはスレッドセーフではありません」) | スレッド安全性は**型**(`Send`/`Sync`)で表現され、コンパイラが検査する | 第8章 |
| GCがあるので参照の生存期間は考えない | 参照の生存期間(ライフタイム)は型の一部 | 第5章 |
| 等価性は`equals`、同一性は`==` | 同一性比較はほぼ使わない。エイリアシング自体が制限されるため | 第4章 |

この表を見て「制約が多いな」と感じたなら、正しい第一印象です。ただし本書を読み終える頃には、これらの制約が**バグのクラスを丸ごと消すための、相互に連携した一つの設計**であることが見えてくるはずです。

> **☕ Javaではこうだった**
> Javaの設計哲学は「実行時の柔軟性を確保し、問題は実行時に検出する」(例外、GC、リフレクション)。Rustの設計哲学は「表現力を制約してでも、問題をコンパイル時に検出する」。どちらが正しいかではなく、どの失敗コストを許容できるかの選択です。

# 第2章 メモリモデルの基礎

**この章を飛ばさないでください。** Javaエンジニアがつまずく原因の8割は、所有権の規則そのものではなく、その前提となるメモリモデルの違いを曖昧にしたまま進むことにあります。

## 2.1 スタック・ヒープ・静的データ領域の役割

プロセスのメモリ空間は、大きく次の領域に分かれます。これはRust固有の話ではなく、ネイティブコードの一般論です。

```text
  高位アドレス
 ┌─────────────────────────┐
 │  スタック(スレッドごと)     │ ← 関数呼び出しごとにフレームを積む
 │        ↓ 伸びる           │    確保・解放はポインタ移動のみ(超高速)
 │                          │    サイズはコンパイル時に既知である必要
 ├─────────────────────────┤
 │        ↑ 伸びる           │
 │  ヒープ                   │ ← 実行時にサイズが決まる/寿命が
 │  (プロセス全体で共有)       │    スコープを超えるデータを置く
 ├─────────────────────────┤    確保・解放にコストがかかる
 │  静的データ領域             │ ← 文字列リテラル、static変数
 │  (.data / .rodata / .bss)│    プログラム終了まで生存
 ├─────────────────────────┤
 │  テキスト領域(機械語コード)  │
 └─────────────────────────┘
  低位アドレス
```

3つの領域の性格を整理します。

| 領域 | 確保コスト | サイズ | 寿命 | 主な用途 |
|---|---|---|---|---|
| **スタック** | ほぼゼロ(SP移動のみ) | コンパイル時に既知 | 関数フレームと同じ | ローカル変数、引数、戻り先 |
| **ヒープ** | あり(アロケータ呼び出し) | 実行時に決定可 | 任意(=誰かが管理する必要) | 可変長データ、長寿命データ |
| **静的領域** | なし(バイナリに埋め込み) | コンパイル時に既知 | プログラム全体 | リテラル、定数、`static` |

**「所有権とは、ヒープ(と各種リソース)の寿命管理の責任を、スタック上の変数に紐づける仕組みである」**——本書を貫く最重要の一文です。スタックは関数の入れ子構造に従って自動的に片付きます。そのスタックの規律に、ヒープの解放を「相乗り」させるのがRustの発想です。

## 2.2 JVMのメモリモデルとの対比

Javaのメモリモデルは、実にシンプルな一枚岩です。

> **プリミティブ型(`int`, `double`, `boolean`…)以外は、すべてヒープ上のオブジェクトであり、変数はそれを指す参照である。**

```java
// Java
Point p = new Point(1, 2);   // Pointオブジェクトはヒープ、pはスタック上の参照
Point q = p;                 // 参照のコピー。オブジェクトは1つのまま
int x = 42;                  // これだけはスタックに値が直接乗る
```

```text
  Javaのモデル(参照の世界)
  スタック              ヒープ
 ┌────────┐        ┌──────────────┐
 │ p ●────┼──┐     │ Point{x:1,y:2}│
 ├────────┤  ├────►│  (+オブジェクト │
 │ q ●────┼──┘     │    ヘッダ)     │
 ├────────┤        └──────────────┘
 │ x  42  │
 └────────┘
```

Rustのモデルは根本的に異なります。

> **変数は値そのものを保持する。その値がヒープを使うかどうかは、型が決める。**

```rust
// Rust
struct Point { x: i32, y: i32 }

let p = Point { x: 1, y: 2 };  // Point全体(8バイト)がスタックに直接乗る
let s = String::from("hello"); // Stringの「管理部」はスタック、文字データはヒープ
```

```text
  Rustのモデル(値の世界)
  スタック                      ヒープ
 ┌─────────────────┐
 │ p: Point         │          (Pointはヒープを使わない)
 │   ┌──────┬─────┐│
 │   │ x: 1 │ y: 2 ││
 │   └──────┴─────┘│
 ├─────────────────┤        ┌───┬───┬───┬───┬───┐
 │ s: String        │   ┌───►│ h │ e │ l │ l │ o │
 │  ┌ptr──┬cap┬len┐│   │    └───┴───┴───┴───┴───┘
 │  │  ●──┼─8─┼─5─┼┼───┘
 │  └─────┴───┴───┘│
 └─────────────────┘
```

この図から読み取るべきことは3つあります。

1. **`Point`にはオブジェクトヘッダも間接参照もない。** Javaなら小さなオブジェクトでもヘッダ(典型的には12〜16バイト)とヒープ確保のコストがかかりますが、Rustの構造体は宣言したフィールドだけのメモリ(この例では8バイト)をスタックに直接置きます。「クラスを細かく分けるとオブジェクトが増えて重くなる」というJavaの感覚は不要です。

2. **`String`は「スタック上の管理部+ヒープ上のデータ」の二階建て。** 管理部は「ヒープへのポインタ、確保容量(capacity)、現在長(length)」の3ワード(64bit環境で24バイト)で、サイズはコンパイル時に確定しています。可変長なのはヒープ側だけです。`Vec<T>`もまったく同じ構造です。

3. **ヒープを使うかどうかは、コードから読み取れる。** `String`や`Vec`や`Box`(第6章)を使えばヒープ、使わなければスタック。Javaのようにエスケープ解析の気まぐれに委ねる部分はありません。

> **☕ Javaではこうだった**
> JavaにもJITのエスケープ解析によるスカラー置換(実質的なスタック割り当て)がありますが、あくまで最適化であり、効くかどうかは保証されません。Rustでは配置が言語仕様のレベルで決まっており、Project Valhalla(値型)がJavaに導入しようとしているものを、Rustは最初から持っていると考えると位置づけが掴みやすいでしょう。

## 2.3 値のサイズとコンパイル時決定 —— `Sized`の入口

スタックに値を直接置くモデルの帰結として、Rustのコンパイラは**あらゆる変数のサイズをコンパイル時に知る必要**があります。関数フレームのレイアウトを機械語生成時に固定するためです。

この要件は`Sized`というマーカートレイトで表現されており、ほとんどの型は自動的に`Sized`です。一方、サイズが定まらない型(**DST**: Dynamically Sized Type)も存在します。

- `str`:文字列スライスの実体。長さは実行時にしか分からない
- `[T]`:配列スライスの実体。同上
- `dyn Trait`:トレイトオブジェクト。実体の型が実行時にしか分からない

DSTは**そのままでは変数に置けず**、必ず「太いポインタ(fat pointer)」越しに扱います。`&str`は「データへのポインタ+長さ」の2ワード、`&dyn Trait`は「データへのポインタ+vtableへのポインタ」の2ワードです。

```rust
let s: str = *"hello";      // コンパイルエラー: strはSizedでない
let s: &str = "hello";      // OK: &strは(ポインタ, 長さ)の2ワードでSized
let b: Box<str> = "hello".into(); // OK: ヒープに置いてポインタで持つ
```

いまの段階では「**変数に直接置けるのはサイズが確定した型だけ。サイズ不定のものはポインタ越しに扱う**」という原則だけ押さえれば十分です。この原則は、第6章で`Box<dyn Trait>`が登場するときに再び効いてきます。

## 2.4 Copy型とMove型の違い

第3章のムーブセマンティクスに入る前に、その分水嶺となる区別を導入します。

Rustの型は、代入時の挙動によって2種類に分かれます。

**Copy型**:代入するとビット列が複製され、**両方の変数が使える**。

- 全整数型(`i32`, `u64`…)、浮動小数点型、`bool`, `char`
- Copy型だけからなるタプルや配列
- 共有参照 `&T`(第4章)

**Move型(非Copy型)**:代入すると所有権が移動し、**元の変数は使えなくなる**。

- `String`, `Vec<T>`, `Box<T>` などヒープ資源を管理する型
- ファイルハンドル、ソケットなどOS資源を管理する型
- 上記を1つでも含む構造体(デフォルト)

なぜこの区別があるのか。判断基準は明快で、**「ビット列の単純コピーで複製が完了する型か?」**です。

`i32`はスタック上の4バイトが全てなので、コピーしても世界に矛盾は生じません。しかし`String`をビットコピーすると何が起きるか、2.2の図で考えてみてください。管理部(ptr, cap, len)が複製され、**2つの管理部が同一のヒープ領域を指す**ことになります。両方がスコープを抜けるとき、同じヒープ領域を2回解放する——古典的な二重解放バグです。

```text
  Stringをビットコピーしてしまった世界(Rustはこれを禁止する)
  スタック                     ヒープ
 ┌──────────────┐
 │ s1:{●,8,5}────┼──┐      ┌───────────┐
 ├──────────────┤  ├─────►│ h e l l o  │ ← 2回解放されたら未定義動作
 │ s2:{●,8,5}────┼──┘      └───────────┘
 └──────────────┘
```

C++はこの問題をコピーコンストラクタ(暗黙のディープコピー)で解決し、「知らないうちに重いコピーが走る」という別の問題を抱えました。Rustの答えは「**単純コピーで安全な型だけコピーを許し、それ以外は移動(ムーブ)を既定とする**」。ディープコピーが必要なら`clone()`と明示的に書かせます(第3章)。

| | Copy型 | Move型 |
|---|---|---|
| 代入・関数渡しの挙動 | ビットコピー(元も使える) | 所有権の移動(元は使用不能) |
| 典型例 | `i32`, `bool`, `char`, `&T` | `String`, `Vec<T>`, `Box<T>`, `File` |
| 複製したいとき | そのまま代入 | `.clone()`を明示 |
| 判定基準 | ビットコピーで矛盾が生じない | 解放責任を伴う資源を管理している |

> **☕ Javaではこうだった**
> Javaの「プリミティブは値渡し、オブジェクトは参照(の値)渡し」という区別と表面上は似ていますが、意味が違います。Javaの参照コピーは「同じオブジェクトへの別名を増やす」操作でした。RustのムーブはCopy型・Move型どちらでも「別名は増やさない」——コピーなら独立した複製ができ、ムーブなら持ち主が交代するだけです。**Rustの代入は、既定ではエイリアス(別名)を作らない**。この一点が、Javaとの最も深い分岐点です。

これで土台が整いました。次章から、いよいよ所有権の規則そのものに入ります。

# 第3章 所有権のコアコンセプト

## 3.1 所有権の3規則

Rustの所有権システム全体は、たった3つの規則の上に建っています。

1. **Rustにおける各値は、「所有者(owner)」と呼ばれる変数を持つ。**
2. **値の所有者は、常にただ一つである。**
3. **所有者がスコープを抜けたとき、値は破棄(drop)される。**

短い規則ですが、含意は深い。規則2は「解放の責任者が常に一意に定まる」ことを意味し、二重解放を原理的に排除します。規則3は「解放のタイミングがソースコードの構造から決定できる」ことを意味し、解放忘れを排除します。

```rust
fn main() {
    let s = String::from("hello"); // sが値の所有者になる
    println!("{s}");
}                                  // sがスコープを抜ける → 値がdropされ、
                                   // ヒープの"hello"が解放される
```

Javaなら「`s`が到達不能になった後、いつかGCが回収する」ところが、Rustでは「`}`の位置で解放コードが実行される」とコンパイル時に確定します。

## 3.2 ムーブセマンティクス —— 代入・関数渡し・戻り値

規則2「所有者は常にただ一つ」を守るために、非Copy型の代入は**所有権の移動(ムーブ)**になります。

```rust
let s1 = String::from("hello");
let s2 = s1;              // 所有権がs1からs2へムーブ

println!("{s1}");         // コンパイルエラー! E0382
```

コンパイラのエラーメッセージを実際に見てみましょう。

```text
error[E0382]: borrow of moved value: `s1`
 --> src/main.rs:4:15
  |
2 |     let s1 = String::from("hello");
  |         -- move occurs because `s1` has type `String`,
  |            which does not implement the `Copy` trait
3 |     let s2 = s1;
  |              -- value moved here
4 |     println!("{s1}");
  |               ^^^^ value borrowed here after move
  |
help: consider cloning the value if the performance cost is acceptable
  |
3 |     let s2 = s1.clone();
  |                ++++++++
```

Javaなら`s2 = s1`の後、両方の変数から同じ文字列を触れました。Rustでは`s1`は「抜け殻」になり、以降のあらゆる使用がコンパイルエラーです。メモリ上で何が起きているかを図にします。

```text
  let s2 = s1; の後
  スタック                        ヒープ
 ┌───────────────────┐
 │ s1: (無効化。使用禁止) │       ┌───────────┐
 ├───────────────────┤   ┌───►│ h e l l o  │
 │ s2: {●, 8, 5}──────┼───┘    └───────────┘
 └───────────────────┘
```

実行時に起きるのは管理部3ワードのコピーだけで、ヒープデータは動きません(ムーブは常に安価な浅いコピーです)。**「ムーブ」の本質は実行時のデータ移動ではなく、「以降どちらの変数が有効か」というコンパイル時の帳簿付けの変更**です。無効化された`s1`に対しては解放コードも生成されないため、二重解放は起こりえません。

ムーブは代入だけでなく、**関数の境界を越えるとき**にも発生します。

```rust
fn take(s: String) {          // 値渡し = 所有権を受け取る
    println!("{s}");
}                             // ここでsがdropされ、ヒープが解放される

fn give() -> String {
    let s = String::from("world");
    s                         // 戻り値としてムーブ(呼び出し側が新所有者に)
}

fn main() {
    let a = String::from("hello");
    take(a);                  // 所有権がtakeへムーブ
    // println!("{a}");       // エラー! aはもう所有者ではない

    let b = give();           // give内で作られた値の所有権を受領
    println!("{b}");
}                             // bがdropされる
```

`take(a)`を呼んだ時点で、`a`の値の解放責任は関数`take`に移りました。だから`take`の終わりで値は解放され、`main`側の`a`は使えません。「関数に値を渡す=その値と今生の別れ(になりうる)」という感覚は、Java にはまったく存在しなかったものです。

「渡した後も使いたい」場合の正攻法は第4章の**借用**ですが、その前に所有権の世界を完結させておきます。

## 3.3 スコープとDrop —— RAIIという規律

規則3「スコープを抜けたら破棄」の破棄処理をカスタマイズするのが`Drop`トレイトです。

```rust
struct Connection { id: u32 }

impl Drop for Connection {
    fn drop(&mut self) {
        println!("接続 {} をクローズ", self.id);
    }
}

fn main() {
    let _c1 = Connection { id: 1 };
    {
        let _c2 = Connection { id: 2 };
        println!("内側ブロック終了直前");
    }                          // ← ここで「接続 2 をクローズ」
    println!("main終了直前");
}                              // ← ここで「接続 1 をクローズ」
```

出力:

```text
内側ブロック終了直前
接続 2 をクローズ
main終了直前
接続 1 をクローズ
```

このパターンはC++由来の**RAII**(Resource Acquisition Is Initialization)と呼ばれます。「リソースの寿命を値の寿命に一致させる」規律で、Rustではこれが言語の基本動作です。

> **☕ Javaではこうだった**
> `AutoCloseable`と`try-with-resources`を思い出してください。
>
> ```java
> try (Connection c = open()) {
>     use(c);
> } // ここでclose()が確実に呼ばれる
> ```
>
> Rustでは**すべての値が暗黙的にtry-with-resources相当**です。`try(...)`の書き忘れという概念がなく、「closeを呼び忘れたリソースリーク」というレビュー指摘項目が消滅します。また、Javaの`finalize()`が抱えていた「いつ呼ばれるか不明・呼ばれない可能性すらある」という問題も存在しません。dropの実行位置はコンパイル時に確定しています。

補足として、明示的に早期解放したい場合は`drop(値)`を呼びます(値をムーブで渡して即座にスコープを終わらせる、只の関数です)。またdropの順序は「**宣言と逆順**」で、これは後から作った値が先に作った値に依存しうるための自然な設計です(第9章で深掘りします)。

## 3.4 `let`と`let mut`、シャドーイング

### 不変がデフォルト

```rust
let x = 5;
x = 6;          // コンパイルエラー! E0384: cannot assign twice to immutable variable

let mut y = 5;
y = 6;          // OK
```

Rustの変数束縛はデフォルトで**不変(immutable)**です。再代入や、値の内部状態の変更(`Vec`へのpushなど)をしたければ`mut`を明示します。

> **☕ Javaではこうだった**
> Javaは「デフォルト可変、`final`でオプトアウト」。Rustは「デフォルト不変、`mut`でオプトイン」。ちょうど鏡像の関係です。近年のJavaスタイルガイドが「実質的にfinalな変数を推奨」する方向に進んでいることを考えると、Rustはその推奨を言語デフォルトに昇格させたと言えます。
>
> ただし重要な違いが一つ。Javaの`final`は「**束縛**の固定」であり、`final List<String> list`でも`list.add()`はできました(参照先オブジェクトは可変)。Rustの不変束縛は「**値**の固定」であり、`let v: Vec<String>`に対する`v.push()`はコンパイルエラーです。Rustの不変は、Javaの`final`よりはるかに強い保証です。

なぜ不変がデフォルトなのか。理由は2つあります。第一に、可読性——`mut`と書かれていない変数は「初期化以降変わらない」と読み飛ばせるため、コードを追う際の認知負荷が激減します。第二に、第4章で見る借用規則との連携——「不変であること」がコンパイラに保証されているからこそ、共有参照を安全に配れるのです。

### シャドーイング

同名の変数を`let`で再宣言できます。これは再代入ではなく、**新しい変数で古い変数を覆い隠す(shadow)**操作です。

```rust
let input = "42";              // &str型
let input: i32 = input.parse().unwrap();  // i32型。前のinputは見えなくなる
let input = input * 2;         // さらに新しい束縛
```

再代入と違って**型を変えられる**点に注目してください。「生の入力→パース済みの値」のように、処理の段階ごとに同じ名前を使い回すイディオムで、`inputStr`, `inputParsed`のような変数名の増殖を防ぎます。`mut`を使わずに済むため、「各段階の値はそれぞれ不変」という保証も保たれます。

## 3.5 Clone / Copy の使い分け

ムーブを避けて独立した複製が欲しいときの選択肢を整理します。

```rust
// Clone: 明示的なディープコピー(ヒープ確保を伴いうる)
let s1 = String::from("hello");
let s2 = s1.clone();           // ヒープデータごと複製。s1もs2も有効
println!("{s1} {s2}");         // OK

// Copy: 暗黙のビットコピー(Copy実装型のみ)
let n1 = 42;
let n2 = n1;                   // i32はCopyなので複製。n1も有効
println!("{n1} {n2}");         // OK
```

自作型への実装は`derive`で行います。

```rust
#[derive(Clone, Copy)]          // CopyはCloneを前提とする(Copy: Clone)
struct Point { x: i32, y: i32 } // 全フィールドがCopyなので可

#[derive(Clone)]                // StringがCopyでないため、CopyはderiveできずCloneのみ
struct User { name: String, age: u32 }
```

設計指針をまとめます。

| 状況 | 推奨 |
|---|---|
| 数値や座標のような小さな純データ型 | `#[derive(Clone, Copy)]`(ムーブの煩わしさが消える) |
| ヒープ資源を含む型 | `Clone`のみderive。複製コストを呼び出し側に明示させる |
| ファイル・ロックなど複製が無意味/危険な資源 | どちらも実装しない(ムーブのみ許す) |
| 「コンパイルを通すためのclone」 | 一時的にはOK。ただし第7章の卒業ロードマップを参照 |

`clone()`の呼び出しがソースコードに必ず現れることには、レビュー上の価値があります。Javaでは「このメソッド呼び出しの裏でdefensive copyが走っているか」はドキュメントを読まないと分かりませんが、Rustでは複製コストの発生地点がgrepできるのです。

# 第4章 借用と参照

第3章の世界だけでは、「値を関数に渡すと戻ってこない」ため実用になりません。所有権を移動させずに値へアクセスする仕組み——それが**借用(borrowing)**です。

## 4.1 共有参照`&T`と可変参照`&mut T`

```rust
fn calc_len(s: &String) -> usize {   // 所有権ではなく共有参照を受け取る
    s.len()
}                                    // sは参照なので、dropしても元の値は無事

fn append(s: &mut String) {          // 可変参照を受け取る
    s.push_str(", world");
}

fn main() {
    let mut s = String::from("hello");
    let len = calc_len(&s);          // &で共有参照を作って渡す(=貸す)
    println!("{s} の長さは {len}");    // sはまだ所有者。普通に使える
    append(&mut s);                  // &mutで可変参照を貸す
    println!("{s}");                 // "hello, world"
}
```

用語を確定させます。

- `&T` —— **共有参照(shared reference)**。参照先を読める。書き換えは不可
- `&mut T` —— **可変参照(mutable reference)**。参照先を読み書きできる
- 参照を作ることを**借用(borrow)**と呼ぶ。「所有権は渡さない、期限付きで貸すだけ」という比喩

参照は実体としては単なるポインタ(またはDST向けの太いポインタ)であり、実行コストはJavaの参照と同等です。違いは実行時ではなく、コンパイル時に課される規則にあります。

## 4.2 借用規則 ——「共有 XOR 可変」

Rustの借用チェッカが強制する規則は、突き詰めれば次の1行です。

> **ある値に対して、任意の時点で有効にできるのは「複数の共有参照(`&T`)」または「ただ一つの可変参照(`&mut T`)」のどちらか一方である。**

さらに、いずれの参照も「参照先の値より長生きしてはならない」(これは第5章のライフタイムの領分)。

|  | 共有参照 `&T` | 可変参照 `&mut T` |
|---|---|---|
| 同時に持てる数 | いくつでも | **1つだけ** |
| 共存 | `&mut`が存在しない間のみ | 他のいかなる参照とも共存不可(所有者による直接アクセスとも排他) |
| できること | 読み取り | 読み書き |

なぜこの規則なのか。答えは「**エイリアシング(別名)と可変性が同時に存在すると、あらゆる地獄が始まる**」からです。抽象論ではピンとこないので、Javaエンジニアなら誰もが踏んだことのある地雷で示します。

```java
// Java: イテレーション中のコレクション変更
List<String> list = new ArrayList<>(List.of("a", "b", "c"));
for (String s : list) {
    if (s.equals("b")) {
        list.remove(s);   // 実行時に ConcurrentModificationException
    }
}
```

このバグの構造は「`list`を読むための別名(イテレータ)と、書き換えるための別名(`list`自身)が同時に活動した」ことです。Javaはこれを**実行時に**検出します(しかも検出は保証されません——ドキュメントいわくbest-effort)。同じことをRustで書くと:

```rust
let mut list = vec!["a", "b", "c"];
for s in &list {                    // listの共有借用がループの間ずっと有効
    if *s == "b" {
        list.retain(|x| *x != "b"); // エラー! E0502
    }
}
```

```text
error[E0502]: cannot borrow `list` as mutable because it is also borrowed as immutable
  |
2 | for s in &list {
  |          ----- immutable borrow occurs here
4 |         list.retain(|x| *x != "b");
  |         ^^^^^^^^^^^^^^^^^^^^^^^^^^ mutable borrow occurs here
```

**同じクラスのバグが、実行時例外からコンパイルエラーに引っ越した**のです。テストで踏むかどうか運任せだった問題が、コードが実行される前に100%検出されます。イテレータ無効化、再ハッシュ中の要素参照、意図しない別名経由の書き換え——「共有XOR可変」は、これら全てをひとつの規則で塞ぎます。

もう一つ、基本例で規則の感触を掴んでください。

```rust
let mut s = String::from("hello");

let r1 = &s;         // OK: 1つ目の共有参照
let r2 = &s;         // OK: 共有参照は何個でも
println!("{r1} {r2}");

let w = &mut s;      // OK: r1, r2はもう使われていないので(→4.4 NLL)
w.push_str("!");
println!("{w}");
```

## 4.3 Javaの参照との決定的な違い

同じ「参照」という言葉を使いますが、性質はまったく異なります。

| 観点 | Javaの参照 | Rustの参照 |
|---|---|---|
| null | ありうる(`NullPointerException`の源泉) | **存在しない**。参照は常に有効な値を指す |
| ダングリング | GCが防ぐ | ライフタイム検査が防ぐ(第5章) |
| エイリアス数 | 無制限。追跡もされない | 借用規則で厳密に管理 |
| 可変性 | 参照経由で常に変更可能(finalフィールド以外) | `&`か`&mut`かで型レベルで区別 |
| 生存期間 | 実行時にGCが判定 | コンパイル時に検査(型の一部) |
| 実行時コスト | ポインタ+GC追跡対象 | ポインタのみ(追跡機構なし) |

特に強調したいのは、**Rustの`&T`は「読み取り専用ビュー」であることが型で保証されている**点です。Javaで`void process(List<String> list)`というシグネチャを見たとき、「このメソッドはlistを変更するのか?」はドキュメントか実装を読まないと分かりません。Rustで`fn process(list: &Vec<String>)`なら、**変更しないことをコンパイラが保証**しています。シグネチャが契約書として機能するのです。

また、`null`が存在しないことは所有権と独立した設計ですが、参照の信頼性を支える双子の柱です。「値がないかもしれない」は`Option<&T>`と型で表現し、コンパイラが「ない場合」の処理漏れを検査します(対応表は第11章)。

## 4.4 参照のスコープとNLL(Non-Lexical Lifetimes)

借用は「いつ終わる」のでしょうか。素朴には「参照変数がスコープを抜けるまで」ですが、現在のRust(2018 Edition以降)はもっと賢く、**「その参照が最後に使用された地点まで」**で借用を終了させます。これをNLL(Non-Lexical Lifetimes)と呼びます。

```rust
let mut s = String::from("hello");

let r = &s;              // 共有借用の開始
println!("{r}");         // rの最後の使用 ← 借用はここで終わる(NLL)

let w = &mut s;          // OK! rの借用はもう終わっているので衝突しない
w.push_str("!");
```

NLL以前のRustではこのコードはエラーでした(`r`の借用がブロック末尾まで続くと解釈されたため)。現在は「使用の実態」に基づいて判定されるので、コンパイラとの不毛な戦いはかなり減っています。

ただし例外として、**`Drop`実装を持つ型はスコープ末尾まで生き続ける**(dropの実行地点が意味を持つため)ことは覚えておいてください。ロックガード(`MutexGuard`)などで「まだ借用が生きている」と言われたら、`drop(guard)`で明示的に終わらせるのが定石です。

## 4.5 借用チェッカのエラーメッセージの読み方

実務での所有権学習は、概念理解2割・エラー解読8割です。rustcのエラーメッセージは業界最高水準に親切なので、**読み方の型**を身につければ大半は自力で解決できます。

エラーメッセージの解剖:

```text
error[E0502]: cannot borrow `list` as mutable because it is also borrowed as immutable
  --> src/main.rs:4:9                       ← (1) 位置
   |
2  |     for s in &list {
   |              ----- immutable borrow occurs here    ← (2) 衝突相手の借用開始点
3  |         if *s == "b" {
4  |             list.retain(|x| *x != "b");
   |             ^^^^ mutable borrow occurs here        ← (3) 問題の操作
5  |     }
   |     - immutable borrow later used here             ← (4) 衝突相手がまだ生きている証拠
```

読む順序は **(3)→(2)→(4)** です。「何をしようとして((3))、何と衝突し((2))、なぜ相手はまだ生きているのか((4))」。特に(4)が重要で、**「その借用はもう終わったはず」と思ったときは、(4)が示す“later used here”の位置を見れば、コンパイラがなぜ借用を延命させたかが分かります**。

主要エラーコードと初動対応の早見表(詳細は第10章):

| コード | 意味 | 初動 |
|---|---|---|
| E0382 | ムーブ済みの値の使用 | 借用(`&`)にできないか検討。だめなら`clone` |
| E0499 | `&mut`の二重借用 | 借用の生存区間を短くする。処理を分割する |
| E0502 | `&`と`&mut`の衝突 | 読み取りを先に済ませて値を取り出す |
| E0505 | 借用中の値のムーブ | 借用の終了後にムーブする |
| E0597 / E0716 | 参照が値より長生き | 値の寿命を延ばす/参照でなく所有で返す |

最後に、エラー番号の詳細は `rustc --explain E0502` でコンパイラ自身に解説させられます。この習慣だけで学習効率が大きく変わります。

# 第5章 ライフタイム

所有権(第3章)と借用(第4章)を学んだ今、最後のピースがライフタイムです。多くの入門者がここで脱落しますが、本章は「暗記」ではなく「何を検査しているのか」の一点から積み上げます。

## 5.1 ライフタイムとは何を検査しているのか

答えを先に言います。ライフタイム検査とは、

> **「すべての参照は、その参照先の値が生きている間しか存在できない」ことの静的な証明**

です。防ぎたいのはダングリング参照——解放済みメモリを指すポインタ——ただ一つです。

Javaにはこの問題が**存在しませんでした**。参照が生きている限りGCがオブジェクトを回収しないため、「参照はあるが実体はもう無い」状況が原理的に作れないのです。GCを持たないRustは、同じ保証を実行時機構ではなく**コンパイル時の証明**で獲得します。これがライフタイムです。

まず、検査が働く最小例:

```rust
fn main() {
    let r;                    // 参照を後で入れる
    {
        let x = 5;
        r = &x;               // xへの参照を作る
    }                         // ← xはここで死ぬ
    println!("{r}");          // エラー! E0597: `x` does not live long enough
}
```

コンパイラの思考はこうです。「`r`は`println!`の行まで生きる必要がある。しかし`r`が指す`x`は内側ブロックで死ぬ。参照が値より長生きするので却下」。すべてのライフタイムの話は、この判定の一般化にすぎません。

## 5.2 ライフタイム注釈の構文と省略規則

関数の中だけなら、コンパイラは値の生死を完全に追跡できます。問題は**関数の境界**です。

```rust
fn longest(x: &str, y: &str) -> &str {          // コンパイルエラー E0106
    if x.len() > y.len() { x } else { y }
}
```

コンパイラは関数を**シグネチャだけで**検査します(実装を見ての全体推論はしません——コンパイル時間と、実装変更が呼び出し側を壊さないという安定性のため)。このシグネチャでは「戻り値の参照は`x`由来か`y`由来か、どれだけ生きられるのか」が宣言されていません。そこでライフタイムパラメータを書きます。

```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

読み方:「あるライフタイム`'a`が存在し、`x`も`y`も少なくとも`'a`の間有効な参照である。戻り値も`'a`の間有効な参照である」。呼び出し側では、`'a`は**`x`と`y`の有効期間の共通部分(短いほう)**に具体化されます。

```rust
let s1 = String::from("long string");
let result;
{
    let s2 = String::from("short");
    result = longest(&s1, &s2);    // 'a = s2の寿命(短いほう)に決まる
    println!("{result}");          // OK: s2はまだ生きている
}
// println!("{result}");           // エラー: 'a(=s2の寿命)を超えて使用
```

### 省略規則(lifetime elision)

「今まで書いた関数に注釈なんて無かったが?」——はい、頻出パターンは省略できるからです。コンパイラは次の規則で自動補完します。

1. 引数の各参照に、それぞれ別のライフタイムを割り当てる
2. 引数の参照が**1つだけ**なら、そのライフタイムを戻り値の全参照に割り当てる
3. メソッドで`&self` / `&mut self`があるなら、**selfのライフタイム**を戻り値に割り当てる

```rust
fn first_word(s: &str) -> &str          // 規則2で fn first_word<'a>(s: &'a str) -> &'a str に補完
impl Config {
    fn name(&self) -> &str              // 規則3で戻り値はselfと同寿命に補完
}
```

`longest`が省略できなかったのは、参照引数が2つあり規則2が使えず、規則3も該当しないためです。**注釈を書かされる=コンパイラが判断を委ねてきた曖昧な状況**、と捉えてください。

## 5.3 関数シグネチャでのライフタイム設計

注釈は「関数が呼び出し側と交わす契約」です。設計の観点で3パターンを比較します。

```rust
// パターンA: 入力と出力を結びつける(最頻出)
fn find<'a>(haystack: &'a str, needle: &str) -> Option<&'a str>
// 「戻り値はhaystackの一部。needleとは無関係」と宣言している。
// needleに'aを付けないことで、呼び出し側は短命な一時文字列をneedleに渡せる。

// パターンB: 全部同じ'aで縛る(過剰な制約になりがち)
fn find<'a>(haystack: &'a str, needle: &'a str) -> Option<&'a str>
// 動くが、「needleもhaystackと同じだけ生きろ」と不要な要求をしている。

// パターンC: 参照を返さない(制約から解放される)
fn find(haystack: &str, needle: &str) -> Option<String>
// 所有された値を返すのでライフタイムは消えるが、ヒープ確保のコストを払う。
```

原則:**ライフタイムパラメータは必要最小限の引数にだけ付ける**。付けた引数と戻り値だけが結び付けられ、それ以外は自由になります。パターンBのような「とりあえず全部`'a`」は、コンパイルは通っても呼び出し側の自由を不必要に奪います。

## 5.4 構造体が参照を持つ場合

構造体のフィールドに参照を持たせる場合も、ライフタイムパラメータが必須です。

```rust
struct Parser<'a> {
    input: &'a str,       // Parserは、どこかにある文字列を借りているだけ
    pos: usize,
}

impl<'a> Parser<'a> {
    fn new(input: &'a str) -> Self {
        Parser { input, pos: 0 }
    }
    fn rest(&self) -> &'a str {      // 戻り値はselfではなくinputの寿命に紐づく
        &self.input[self.pos..]
    }
}
```

`Parser<'a>`という型は「**寿命`'a`の文字列を借りている間しか存在できないParser**」を意味します。構造体インスタンスが参照先より長生きすることを、型システムが禁止します。

```rust
let p;
{
    let text = String::from("hello world");
    p = Parser::new(&text);
}                                    // textが死ぬ
// p.rest();                          // エラー: pはtextより長生きできない
```

設計指針として、**参照を持つ構造体は「短命な作業用ビュー」に限定する**のが健全です(パーサ、イテレータ、設定のビューなど)。長寿命のドメインオブジェクトに参照フィールドを持たせると、アプリ全体がライフタイムパズルと化します。長寿命の構造体には所有された値(`String`, `Vec<T>`)を持たせるのが定石です(アンチパターンの詳細は第10章)。

## 5.5 `'static`の2つの意味

特別なライフタイム`'static`は文脈により2つの顔を持ち、混同が事故のもとなので明確に分けます。

**顔1:参照の型として——「プログラム終了まで有効な参照」**

```rust
let s: &'static str = "hello";   // 文字列リテラルは静的領域(2.1)にあるため'static
```

**顔2:トレイト境界として——「借用を含まない型」**

```rust
fn spawn<F: FnOnce() + Send + 'static>(f: F)   // std::thread::spawnのシグネチャ(要旨)
```

この`'static`は「`F`は`'static`参照しか持たない=**一時的な借り物を含まない、自己完結した値**」という意味です。所有された`String`や`Vec<i32>`は借用を含まないので`'static`境界を満たします(「プログラム終了まで生きるデータ」という意味では**ありません**)。

スレッド生成でこの境界が要求される理由は素直で、「新スレッドがいつまで走るか分からない以上、親スタックの借り物を持ち込ませるわけにはいかない」からです。`thread::spawn`で`'static`エラーに遭遇したら、「借用ではなく所有権ごと渡せ(`move`)」がほぼ常に答えです(第8章)。

## 5.6 核心:「注釈は制約の記述であって、寿命の操作ではない」

本章で最も重要な一文です。

> **ライフタイム注釈は、値の寿命を1ミリ秒も延ばさないし縮めない。実行コードを1バイトも生成しない。注釈は「既に存在する寿命関係についての、コンパイラへの申告」である。**

初学者の典型的な誤解は「`'a`を工夫すれば寿命を延ばせるのでは」というものです。できません。値の寿命は所有権の規則(スコープとムーブ)だけで決まっており、注釈はその**既成事実をシグネチャという契約書に書き写す行為**にすぎません。

だからライフタイムエラーへの正しい対処は、注釈をこねくり回すことではなく、

1. 契約(シグネチャ)が実態と合っているかを直す —— 5.3のパターンA/Bの違い
2. それでも駄目なら、**寿命の実態そのもの**を変える —— 値の宣言位置を外側に出す、参照でなく所有で持つ/返す

の二択です。ジェネリクスの`<T: Comparable<T>>`が「Tに課す制約の申告」であってTを変化させないのと同型だ、と理解すると、Javaエンジニアにはしっくり来るはずです。ライフタイムとは、**型パラメータの時間版**なのです。

# 第6章 スマートポインタと内部可変性

第3〜5章の規則——単一所有・共有XOR可変・参照は値より短命——は強力ですが、正当な理由でこの規則を「緩めたい」場面が実務には存在します。本章で扱う型たちは便利グッズの寄せ集めではなく、**「どの規則を、どこまで、どんな代償で緩めるか」の体系**です。この軸で眺めると全体が一枚の地図になります。

| 型 | 緩める規則 | 移す先 | 代償 |
|---|---|---|---|
| `Box<T>` | (何も緩めない。配置だけ変える) | — | ヒープ確保1回 |
| `Rc<T>` / `Arc<T>` | 「所有者は1人」→ 複数所有 | 実行時(参照カウント) | カウント操作コスト、循環リークのリスク |
| `Cell<T>` / `RefCell<T>` | 「共有XOR可変」→ 共有しつつ変更 | 実行時(`RefCell`は借用カウント) | `RefCell`は違反時**パニック** |
| `Mutex<T>` / `RwLock<T>` | 同上(スレッド跨ぎ版) | 実行時(ロック) | ブロッキング、デッドロックのリスク |

## 6.1 `Box<T>` —— 最も素朴なヒープ確保

`Box<T>`は「値をヒープに置き、そのポインタを単一所有する」だけの型です。所有権の規則は一切変わりません(所有者は1人、スコープを抜けたらヒープごと解放)。

```rust
let b = Box::new(42);        // i32をヒープに確保
println!("{}", *b);          // *で中身へ。実際は自動derefで b でも動く場面が多い
```

「わざわざヒープに置く」動機は主に3つです。

**(1) 再帰型のサイズを確定させる**

```rust
// enum List { Cons(i32, List), Nil }      // エラー: サイズが無限に再帰する
enum List { Cons(i32, Box<List>), Nil }    // OK: Boxはポインタ1個分でサイズ確定
```

2.3の`Sized`の話がここで効きます。型のサイズはコンパイル時に確定が必要で、自分自身を直接含む型は定義できません。ポインタを挟めばサイズは1ワードに確定します。連結リストや木構造の定義に必須です。

**(2) トレイトオブジェクト(実行時ポリモーフィズム)**

```rust
trait Shape { fn area(&self) -> f64; }

let shapes: Vec<Box<dyn Shape>> = vec![
    Box::new(Circle { r: 1.0 }),
    Box::new(Square { s: 2.0 }),
];
for s in &shapes { println!("{}", s.area()); }
```

`dyn Shape`はサイズ不定(実体の型が実行時までわからない)なので、`Box`に入れてサイズを確定させます。これがJavaの`List<Shape>`(インターフェース型のコレクション)に最も近い書き方です。Javaでは全オブジェクトが暗黙にこの形(ヒープ+動的ディスパッチ)でしたが、Rustではオプトインであり、`Box<dyn Trait>`という字面が「ここで仮想呼び出しのコストを払う」と明示します。

**(3) 巨大な値のムーブを安価にする**:大きな構造体をムーブすると管理部でなく全体のコピーが走るため、`Box`に入れてポインタ1個のムーブに変える最適化です。

## 6.2 `Rc<T>` / `Arc<T>` —— 複数所有への回帰と、その落とし穴

「所有者は常に1人」では表現しづらいデータもあります。典型はグラフ構造や、複数のコンポーネントが同じ設定オブジェクトを保持するケースです。`Rc<T>`(Reference Counted)は**参照カウント方式の複数所有**を提供します。

```rust
use std::rc::Rc;

let config = Rc::new(Config { timeout: 30 });   // カウント=1
let for_client = Rc::clone(&config);            // カウント=2(データはコピーされない)
let for_server = Rc::clone(&config);            // カウント=3

drop(for_client);                               // カウント=2
// 全Rcがdropされ、カウントが0になった瞬間にConfig本体が解放される
```

`Rc::clone`はヒープデータを複製せず、カウンタをインクリメントしてポインタを複製するだけです(だから慣習として`config.clone()`でなく`Rc::clone(&config)`と書き、「安いクローンだ」と読み手に伝えます)。

> **☕ Javaではこうだった**
> `Rc<T>`は「複数の変数から同じオブジェクトを共有する」というJavaの日常への、**部分的な**回帰です。ただし2つの決定的な違いがあります。第一に、共有される`T`は**不変**です(`Rc`は共有参照しか取り出せないので、借用規則により変更不可。変更したければ6.3と組み合わせます)。第二に、回収は到達可能性ベースのGCではなく参照カウントです。この方式の弱点が次の循環参照です。

### 循環参照とWeak

```rust
use std::rc::{Rc, Weak};
use std::cell::RefCell;

struct Node {
    value: i32,
    children: Vec<Rc<Node>>,       // 親→子: 強参照(所有)
    parent: RefCell<Weak<Node>>,   // 子→親: 弱参照(所有しない)
}
```

親→子と子→親を両方`Rc`にすると、互いのカウントが1未満に下がらず、**両者とも永久に解放されません**。GC言語では起こらなかった種類のリークです(JavaのGCは「rootから到達できるか」で判定するため、孤立した循環は回収されます)。

対策が`Weak<T>`(弱参照)です。カウントに数えられず、参照先が生きていれば`upgrade()`で`Option<Rc<T>>`が取れ、死んでいれば`None`が返ります。設計原則は「**所有の方向を一方通行にし、逆向きの辿りはWeakにする**」。親子・キャッシュ・オブザーバなど「逆リンク」が欲しい場面の定石です。Javaの`WeakReference`(キャッシュでGCを妨げないために使った)と発想は同じで、こちらは必需品である点が違います。

### `Arc<T>` —— スレッド安全版

`Rc`のカウント操作は非アトミックで、シングルスレッド専用です(スレッドを跨ごうとするとコンパイルエラーになります——第8章の`Send`)。マルチスレッドで共有するなら`Arc<T>`(Atomically Reference Counted)を使います。機能は同一で、カウント操作がアトミック命令になるぶん僅かに重い。「まず`Rc`、スレッドを跨ぐ必要が出たらコンパイラに叱られてから`Arc`に替える」で実務上問題ありません。

## 6.3 内部可変性 —— `Cell<T>`と`RefCell<T>`

いよいよ「共有XOR可変」の緩和です。**内部可変性(interior mutability)**とは、「共有参照(`&`)越しに中身を変更できる」性質を持つ型のことです。

「規則を破っているのでは?」——いいえ。借用規則の目的(4.2)は「別名と可変性の無秩序な同居を防ぐ」ことでした。内部可変性の型は、その検査を**コンパイル時から実行時に移す**ことで、安全性を保ったまま柔軟性を得ます。

### `Cell<T>` —— 値の出し入れだけを許す

```rust
use std::cell::Cell;

struct Counter { count: Cell<u32> }

impl Counter {
    fn increment(&self) {                    // &mut selfでなく&selfな点に注目
        self.count.set(self.count.get() + 1);
    }
}
```

`Cell<T>`は中身への**参照を一切外に出さず**、`get`(Copyして取り出す)と`set`(丸ごと差し替える)しか許しません。参照が外に漏れない以上、別名経由の矛盾は構造的に起こりえない——だから実行時検査すら不要でゼロコストです。用途は`Copy`な小さい値(カウンタ、フラグ、キャッシュ済み計算値)に限られます。

### `RefCell<T>` —— 借用検査の実行時移管

参照を取り出したい大きな値には`RefCell<T>`を使います。借用規則そのもの(共有は複数、可変は1つ、両立不可)を、**実行時のカウンタで検査**します。

```rust
use std::cell::RefCell;

let data = RefCell::new(vec![1, 2, 3]);

{
    let r1 = data.borrow();       // 実行時に共有借用を記録(Ref<T>が返る)
    let r2 = data.borrow();       // OK: 共有は複数可
    println!("{} {}", r1.len(), r2.len());
}                                 // Refがdropされ、借用記録が解除される

data.borrow_mut().push(4);        // OK: 他の借用が無いので可変借用できる

let r = data.borrow();
let w = data.borrow_mut();        // コンパイルは通るが、実行時に panic!
                                  // "already borrowed: BorrowMutError"
```

最後の2行が`RefCell`の代償の全てです。**借用規則違反が、コンパイルエラーから実行時パニックに変わる**。つまりRustの最大の売り(静的検査)を局所的に手放す取引であり、だからこそ使用範囲は最小限に絞るべきです。`borrow()`/`borrow_mut()`の呼び出しが字面に残るため、レビューで「ここは実行時検査に頼っている」と識別できることがせめてもの救いです。

### なぜこんな仕組みが必要なのか

正当な用途は「**外形上は不変(`&self`)だが、内部の帳簿は更新したい**」場面です。キャッシュ(メモ化)、遅延初期化、モックオブジェクトの呼び出し記録、コールバック登録簿など。Javaでは「不変っぽいクラスの中の`private`な可変フィールド」として無意識にやっていたことに、Rustは明示的な名前と検査を与えたのだと考えてください。

## 6.4 `Mutex<T>` / `RwLock<T>`との関係

実は読者はもう`Mutex`を理解しています。**`Mutex<T>`とは「スレッド安全版の`RefCell<T>`」**だからです。

| | `RefCell<T>` | `Mutex<T>` |
|---|---|---|
| 検査方法 | 借用カウンタ | OSレベルのロック |
| 違反時 | 即パニック | **ブロック(待つ)** |
| スレッド | 単一のみ | 複数OK |
| 取り出すガード | `Ref` / `RefMut` | `MutexGuard` |
| 典型の相方 | `Rc<RefCell<T>>` | `Arc<Mutex<T>>` |

`RwLock<T>`は「共有(読み)は複数、可変(書き)は1つ」という借用規則をロックとして実装したもので、対応はさらに直接的です。

注目すべきは`Mutex<T>`が**データを中に包んでいる**設計です。Javaの`synchronized`はコードブロックを守る仕組みで、「どのデータがどのロックで守られているか」は規約とJavadocの世界でした(「このフィールドへのアクセスはlockを保持して行うこと」)。Rustでは**ロックを取らない限りデータに触れる方法が型システム上存在しません**。ロック忘れというバグのクラスが消滅します(第8章で詳述)。

## 6.5 組み合わせパターンと選択フローチャート

これらの型は組み合わせて使います。頻出形を挙げます。

| パターン | 意味 | 典型用途 |
|---|---|---|
| `Box<T>` | 単一所有・ヒープ配置 | 再帰型、トレイトオブジェクト |
| `Rc<T>` | 複数所有・不変・単一スレッド | 共有設定、イミュータブルな木 |
| `Rc<RefCell<T>>` | 複数所有・可変・単一スレッド | GUIの状態、グラフの可変ノード |
| `Arc<T>` | 複数所有・不変・マルチスレッド | スレッド間で読み共有する設定 |
| `Arc<Mutex<T>>` | 複数所有・可変・マルチスレッド | スレッド間の共有可変状態 |
| `Rc<T>`+`Weak<T>` | 複数所有+非所有の逆リンク | 親子構造、キャッシュ |

選択フローチャート:

```text
値をどう扱いたい?
│
├─ ヒープに置きたいだけ/再帰型/dyn Trait ────────────► Box<T>
│
├─ 所有者を複数にしたい
│   ├─ 中身の変更は不要
│   │    ├─ 単一スレッド ──────────────────────────► Rc<T>
│   │    └─ スレッドを跨ぐ ────────────────────────► Arc<T>
│   └─ 中身も変更したい
│        ├─ 単一スレッド
│        │    ├─ 中身がCopyな小さい値 ──────────────► Rc<Cell<T>>
│        │    └─ それ以外 ─────────────────────────► Rc<RefCell<T>>
│        └─ スレッドを跨ぐ
│             ├─ 読みが圧倒的に多い ────────────────► Arc<RwLock<T>>
│             └─ 通常 ────────────────────────────► Arc<Mutex<T>>
│
└─ 所有者は1人のままでよい ──► そもそも本章の型は不要。&/&mutで足りないか再考
```

### `Rc<RefCell<T>>`はいつ正当か

表の中で最も注意が要るのが`Rc<RefCell<T>>`です。これは「複数の場所から同じオブジェクトを参照し、どこからでも変更できる」——つまり**Javaの通常のオブジェクト共有をほぼ再現する装置**です。

Javaの世界を持ち込める快適さの代償に、Rustが静的に保証してくれていたものを2つ(単一所有・静的借用検査)とも実行時に押し戻しています。**至る所が`Rc<RefCell<T>>`だらけになってきたら、それは道具の問題ではなく設計の問題**——「誰がデータを所有するのか」の設計をJavaの感覚のまま持ち込んでいるサインです。所有の階層を作り直す・IDで間接参照する等の代替設計は第10章(10.3)で扱います。正当な使い所は、真に共有可変が本質であるドメイン(GUIウィジェットツリー、インタプリタの環境など)に限られます。

# 第7章 実践パターン:所有権を意識したAPI設計

規則は理解した。しかし自分で書くと手が止まる——本章はその谷を埋める、実務パターン集です。

## 7.1 関数の引数設計 —— `T`か`&T`か`&mut T`か

Rustでは引数の型そのものがAPIの意味論を語ります。設計判断の基準はこうです。

| 引数の型 | 呼び出し側から見た意味 | 使うべき場面 |
|---|---|---|
| `T`(値渡し) | 「その値、**もらいます**」 | 関数が値を消費・変換・保管する(コンストラクタ、ビルダー、`into_*`系) |
| `&T` | 「**見せてもらう**だけ」 | 読み取りのみ(計算、検索、フォーマット) |
| `&mut T` | 「**その場で書き換えます**」 | 更新(ソート、push、フィールド変更) |

```rust
struct User { name: String }

impl User {
    fn new(name: String) -> Self {        // 所有権を取る: 値を保管するから
        User { name }
    }
    fn greet(&self) -> String {           // &self: 読むだけだから
        format!("Hello, {}", self.name)
    }
    fn rename(&mut self, name: String) {  // &mut self: 更新するから
        self.name = name;
    }
}
```

`new`が`&str`でなく`String`を取るのは意図的です。構造体は`String`を保持するので、どのみち所有された`String`が必要になります。`&str`で受けて内部で`to_string()`すると、呼び出し側が既に`String`を持っていた場合に**無駄な複製を強制**します。`String`で受ければ、持っている人はムーブで渡せ(コピーゼロ)、`&str`しか無い人は自分で`to_string()`して渡す——コストの支払いが適材適所になります。

> **☕ Javaではこうだった**
> Javaのシグネチャ`void process(List<String> list)`からは「listは読まれるのか、変更されるのか、保持され続けるのか」が読み取れず、防御的コピーをすべきかはJavadoc頼みでした。Rustでは`&Vec<..>`/`&mut Vec<..>`/`Vec<..>`の3択が**その契約を型で公開**します。シグネチャレビューだけで副作用の範囲が確定するのは、大規模開発で効く性質です。

## 7.2 `String`と`&str`、`Vec<T>`と`&[T]`

新人Rustaceanの最初の混乱ポイントですが、構図は一つです。

```text
  所有バッファ型            借用ビュー型(スライス)
  String  ────&を取ると────►  &str      (文字列)
  Vec<T>  ────&を取ると────►  &[T]      (配列)
```

- `String`/`Vec<T>`:ヒープバッファを**所有**する。伸長できる。dropで解放される
- `&str`/`&[T]`:どこかにあるデータの**連続領域を指すビュー**(ポインタ+長さ)。文字列リテラル、`String`の一部、`Vec`の一部、どれでも指せる

**引数で受けるときの原則:借用して読むだけなら、ビュー型で受ける。**

```rust
fn count_words(s: &String) -> usize   // ✗ Stringからしか呼べない
fn count_words(s: &str) -> usize      // ✓ String(＆自動変換), リテラル, 部分文字列すべてOK
```

`&String`で受けるメリットは何一つなく、`&str`はderef強制により`&String`からも自動で作られるため、**読み取り引数は常に`&str` / `&[T]`**が正解です。clippy(標準の静的解析)も`&String`引数を警告します。

まとめの早見表:

| 場面 | 文字列 | 配列 |
|---|---|---|
| 構造体フィールド(長寿命) | `String` | `Vec<T>` |
| 読み取り引数 | `&str` | `&[T]` |
| 更新する引数 | `&mut String` | `&mut Vec<T>` |
| 所有権ごと受け取る引数 | `String` | `Vec<T>` |
| 戻り値(新規生成) | `String` | `Vec<T>` |
| 戻り値(入力の一部) | `&str`+ライフタイム | `&[T]`+ライフタイム |

## 7.3 「とりあえずclone」からの卒業ロードマップ

正直に言いましょう。**Java経験者は最初、cloneまみれのコードを書きます。それでいいのです。** 恥じて質問できなくなるより、段階を踏んで卒業するほうが健全です。

**第1段階:cloneで動かす(最初の1〜2ヶ月)**
借用エラーが出たら`clone()`で黙らせて前に進む。この段階の目的は所有権ではなく、Rustの他の要素(enum、パターンマッチ、トレイト)に慣れることです。cloneは遅いといっても「正しく動く遅いコード」であり、未定義動作とは次元が違います。

**第2段階:「読むだけの箇所」から借用に置き換える(パターン認識期)**
最も機械的に直せるのは「関数に渡すためのclone」です。

```rust
process(data.clone());     // before: 渡した後もdataを使いたいのでclone
process(&data);            // after: 関数側を fn process(d: &Data) に変えるだけ
```

grepで`.clone()`を洗い出し、「渡した先で所有が本当に必要か?」を一つずつ問う。8割は`&`で置き換わります。

**第3段階:データの持ち方を設計する(構造期)**
残ったcloneは「同じデータを複数の場所が持ちたい」という設計要求の現れです。ここで初めて第6章(`Rc`/`Arc`)や、「そもそも所有者を1人に整理し直す」設計(10.3)を検討します。

重要な心構えを一つ。**cloneを消すのはパフォーマンス最適化である前に、設計の明確化です**。「この関数はデータを読むだけ」「この構造体がこのデータの持ち主」という事実がコードに刻まれること自体に価値があり、速度はその副産物と考えてください(実測で問題になるcloneは、ループ内の大きな`Vec`/`String`のcloneくらいです)。

## 7.4 イテレータと所有権

コレクションの走査には3つのモードがあり、所有権の3形態と正確に対応します。

| メソッド | 要素の型 | 意味 | for構文の糖衣 |
|---|---|---|---|
| `iter()` | `&T` | 借りて読む | `for x in &v` |
| `iter_mut()` | `&mut T` | 借りて書き換える | `for x in &mut v` |
| `into_iter()` | `T` | 所有権ごと取り出す(元のコレクションは消費される) | `for x in v` |

```rust
let v = vec![String::from("a"), String::from("b")];

for s in &v { println!("{s}"); }        // 借用。ループ後もvは使える
for s in v { println!("{s}"); }         // ムーブ。ループ後、vはもう無い!
// println!("{:?}", v);                  // エラー E0382
```

`for x in v`と書いた瞬間に`v`が消費される——Javaの拡張for文(常に借用相当)の感覚でいると必ず一度は踏むエラーです。イテレータチェーンでも同じ区別が貫かれます。

```rust
// 借用ベース: vは残る。ただしresultはvへの参照を含む(ライフタイム発生)
let result: Vec<&String> = v.iter().filter(|s| s.len() > 1).collect();

// 所有ベース: vは消費されるが、resultは自己完結した所有データになる
let result: Vec<String> = v.into_iter().filter(|s| s.len() > 1).collect();
```

「元のコレクションはもう要らず、加工結果だけ欲しい」パイプライン処理では`into_iter`が自然で、ライフタイムも登場しません。**変換の連鎖では所有権も一緒に流す**、と覚えてください。

## 7.5 構造体設計のパターン

**(1) 所有の階層(ツリー)を作る**
健全なRustプログラムのデータは、所有関係が木構造を成します。

```rust
struct App {                 // Appが全体を所有する(root)
    config: Config,
    db: Database,
    server: Server,
}
```

処理で横断的なアクセスが必要なときは、フィールドの参照を**一時的に**関数へ渡します。「`Server`が`Config`への参照を恒久的に保持する」設計(Javaでは普通のDI)を避け、「必要な瞬間だけ`&Config`を引数で渡す」に倒すのがコツです。

**(2) 自己参照構造体を避ける**
「フィールドAが、同じ構造体のフィールドBの一部を指す」構造は、safe Rustでは作れません(構造体がムーブされると参照が壊れるため)。

```rust
struct Bad {
    data: String,
    view: &str,        // dataの一部を指したい → 不可能(ライフタイムが書けない)
}
```

代替は「**参照でなくインデックスで持つ**」です。

```rust
struct Good {
    data: String,
    view: std::ops::Range<usize>,   // 位置情報だけ持ち、必要時に &data[range] で切り出す
}
```

**(3) 部分借用を意識してフィールドを分ける**
借用チェッカは「構造体の別フィールドへの同時借用」を、同一関数内では区別できます(`&mut self.a`と`&self.b`は共存可)が、メソッド呼び出し(`&mut self`)を挟むと構造体全体の借用になります。更新系ロジックが複雑な構造体は、関連フィールドをサブ構造体にまとめておくと、借用の粒度が細かくなり衝突が減ります。

## 7.6 エラー処理と`?`演算子における値の移動

Rustのエラー処理`Result<T, E>`も所有権と無縁ではありません。`?`演算子は「`Err`なら**その値をムーブして**early return、`Ok`なら中身を**ムーブで取り出す**」操作です。

```rust
fn load(path: &str) -> Result<Config, io::Error> {
    let text = std::fs::read_to_string(path)?;  // Ok(String)から中身がムーブされてtextへ
    let config = parse(&text)?;                 // textは借用で渡す(後で使わないならムーブでも可)
    Ok(config)                                  // configの所有権を呼び出し側へ
}
```

注意点は2つ。第一に、`Result`を`?`や`match`で分解した時点で中身はムーブ済みなので、元の`Result`変数は使えません。第二に、エラー型`E`も所有された値としてreturnに乗って旅をするため、エラー型に借用(`&str`など)を含めると、エラーがエラー発生源の関数を出られなくなります。**エラー型は`String`や専用enumなど、自己完結した(`'static`な)所有データにする**のが定石です(`thiserror`等のデファクトのクレートもこの前提で設計されています)。

# 第8章 並行処理と所有権

所有権システムの真価が最も劇的に現れるのが並行処理です。長年マルチスレッドのバグと格闘してきたシニアエンジニアほど、本章の内容には驚くはずです。

## 8.1 `Send`と`Sync` —— スレッド安全性を型にする

Rustはスレッド安全性を、2つのマーカートレイトとして型システムに組み込んでいます。

- **`Send`**:その型の値の**所有権を別スレッドに移してよい**
- **`Sync`**:その型への**共有参照(`&T`)を複数スレッドから同時に使ってよい**(定義上、`T: Sync` ⇔ `&T: Send`)

ほとんどの型(`i32`, `String`, `Vec<T>`…)は自動的に両方を満たします。満たさない型の代表が、第6章で「単一スレッド専用」と述べた型たちです。

| 型 | Send | Sync | 理由 |
|---|---|---|---|
| `i32`, `String`, `Vec<T>` | ✓ | ✓ | 共有可変状態を含まない |
| `Rc<T>` | ✗ | ✗ | 参照カウントが非アトミック |
| `Cell<T>`, `RefCell<T>` | ✓ | ✗ | 借用検査/値の出し入れが非スレッド安全 |
| `Arc<T>` (T: Send+Sync) | ✓ | ✓ | カウントがアトミック |
| `Mutex<T>` (T: Send) | ✓ | ✓ | ロックで直列化される |
| `MutexGuard<T>` | ✗ | ✓ | ロックの取得スレッドと解放スレッドは同一であるべき |

決定的に重要なのは、これが**ドキュメントではなく検査対象**だという点です。`thread::spawn`のシグネチャには`F: Send + 'static`という境界があり、`Send`でない値をクロージャに含めた瞬間、コンパイルが通りません。

```rust
use std::rc::Rc;
use std::thread;

let data = Rc::new(vec![1, 2, 3]);
thread::spawn(move || {
    println!("{:?}", data);   // エラー! E0277: `Rc<Vec<i32>>` cannot be sent
});                           //   between threads safely
```

エラーメッセージは「`Rc`は`Send`じゃない。`Arc`を検討せよ」と教えてくれます。**「この型をスレッドに渡していいか」を人間が判断する必要がない**——これがどれほどのことか、`SimpleDateFormat`をstaticフィールドに置いて本番障害を起こした経験のあるチームなら分かるはずです。

> **☕ Javaではこうだった**
> Javaのスレッド安全性は文書規約でした。「このクラスはスレッドセーフです」「外部同期が必要です」というJavadocの一文、`@ThreadSafe`/`@NotThreadSafe`アノテーション(検査はされない)、そして『Java並行処理プログラミング』を読んだ人の注意力。`HashMap`をマルチスレッドで使ってしまうミスを、コンパイラは止めてくれませんでした。Rustでは`HashMap`は`Sync`ですが「`&mut`は1つ」の規則があるため、同期機構なしに複数スレッドから書き込むコードは**そもそも型が合いません**。

## 8.2 スレッド間の所有権の移動

### `move`クロージャ

`thread::spawn`の`'static`境界(5.5)は「親スタックの借り物を新スレッドへ持ち込むな」を意味しました。したがってスレッドへのデータの渡し方の基本は**所有権ごと移す**ことで、それを指示するのが`move`キーワードです。

```rust
let data = vec![1, 2, 3];

let handle = thread::spawn(move || {      // moveでdataの所有権をクロージャへ
    println!("{:?}", data);               // 新スレッドがdataの新しい所有者
});

// println!("{:?}", data);                // エラー: dataはもうこのスレッドに無い

handle.join().unwrap();
```

なぜ借用ではだめか。親スレッドの関数が先に終われば、`data`はスタックごと消え、子スレッドはダングリング参照を握ります。C++でもJava(final変数キャプチャの意味論は違えど)でも「スレッドと寿命」の問題は運用で回避してきましたが、Rustは型で禁止します。なお「スコープの終わりで必ずjoinする」ことを型で保証する`std::thread::scope`を使えば、借用のままスレッドに渡すことも安全にできます(コンパイラがちゃんと許します)。

### チャネル —— 所有権を送る通信

「メモリを共有して通信するな。通信してメモリを共有せよ」(Go言語の標語)は、Rustでは所有権と融合してさらに強い形になります。

```rust
use std::sync::mpsc;

let (tx, rx) = mpsc::channel();

thread::spawn(move || {
    let msg = String::from("hello");
    tx.send(msg).unwrap();          // msgの所有権がチャネルの中へムーブ
    // println!("{msg}");           // エラー: 送った値はもう触れない
});

let received = rx.recv().unwrap();  // 受信側が新しい所有者になる
println!("{received}");
```

`send`が所有権を奪うことに注目してください。**送信後に送信側が値を触り続ける**——メッセージパッシング設計における古典的なバグ(共有オブジェクトを送ってしまい、送信後の変更が受信側に化けて見える)が、型レベルで不可能になっています。

### 共有可変状態:`Arc<Mutex<T>>`

どうしても状態を共有したい場合の定石が第6章の表にあった`Arc<Mutex<T>>`です。

```rust
use std::sync::{Arc, Mutex};

let counter = Arc::new(Mutex::new(0));
let mut handles = vec![];

for _ in 0..10 {
    let counter = Arc::clone(&counter);        // 各スレッド用に所有権(カウント)を複製
    handles.push(thread::spawn(move || {
        let mut n = counter.lock().unwrap();   // ロック取得。ガードが返る
        *n += 1;
    }));                                       // ガードのdropでロック解放(RAII!)
}

for h in handles { h.join().unwrap(); }
println!("{}", *counter.lock().unwrap());      // 10
```

観察してほしい点が3つあります。

1. **ロック解放が自動**:`MutexGuard`のdrop(第3章のRAII)で解放されるので、`unlock`忘れ・例外経路での解放漏れがありません。Javaの`try { } finally { lock.unlock(); }`定型文は不要です。
2. **ロックなしにデータへ到達する経路が存在しない**:`Mutex<T>`が`T`を内包しているため(6.4)、「ロックを取り忘れて直接触る」コードは書けません。
3. **`Mutex`を外したらコンパイルエラー**:`Arc<i32>`のまま`*n += 1`しようとすると「共有参照越しの変更」で弾かれます。同期機構は「付けたほうがよい」ではなく「付けないと型が合わない」のです。

## 8.3 Javaの並行処理モデルとの対応表

| Javaの道具 | Rustの対応物 | 主な違い |
|---|---|---|
| `synchronized`ブロック / `ReentrantLock` | `Mutex<T>` | データを内包する。解放はRAII。再入不可(再入は設計臭としてあえて非対応) |
| `ReadWriteLock` | `RwLock<T>` | 同上 |
| `volatile` / `Atomic*` | `std::sync::atomic::*` | ほぼ同等(メモリオーダリングを明示的に選ぶ) |
| `BlockingQueue` | `mpsc::channel` / crossbeam | sendで所有権が移動する |
| `ExecutorService` | rayon(データ並列)/ tokio(非同期) | 標準外だがデファクト |
| `ThreadLocal` | `thread_local!` | ほぼ同等 |
| `ConcurrentHashMap` | `DashMap`(クレート)/ `RwLock<HashMap>` | 標準には無い |
| `CompletableFuture` | `Future` + async/await | 実行にはランタイム(tokio等)が必要 |
| `@GuardedBy("lock")`(規約) | `Mutex<T>`が守るデータを型で内包 | **規約が型に昇格** |
| メモリモデル(JMM, happens-before) | C++20相当のメモリモデル | 概念はほぼ共通。JMMの知識は直接活きる |

最後の行は朗報です。happens-before関係、可視性、リオーダリングといったJMMで培った理解は、Rustのアトミックとメモリオーダリング(`Ordering::Acquire`/`Release`/`SeqCst`)にほぼそのまま転用できます。シニアエンジニアの既存知識が最も高く売れる領域です。

## 8.4 「Fearless Concurrency」の実像

Rustは自らの並行処理を"Fearless Concurrency"(恐れなき並行性)と呼びます。正確な理解のため、保証の境界線を引いておきます。

**防げるもの:データ競合(data race)**

データ競合とは「複数スレッドが同じメモリ位置に同期なしにアクセスし、少なくとも1つが書き込みである」状況で、未定義動作の源泉です。safe Rustではこれが**コンパイル時に排除**されます。仕組みは本章で見てきた通り、「共有XOR可変」(第4章)+「Send/Sync」の合わせ技であり、新しい魔法ではなく**所有権システムの自然な帰結**です。

**防げないもの:**

- **デッドロック**:2つの`Mutex`を逆順に取れば普通に固まります。ロック順序の規律は依然として人間の仕事です。
- **レースコンディション一般**:「残高を確認してから引き落とす」の2操作の間に他スレッドが割り込む——個々の操作が同期されていても、**操作列の原子性**は型では表現されていません(check-then-actはロックの粒度設計の問題として残ります)。
- **ライブロック、飢餓、性能問題**:同上。

つまりFearlessの正確な意味は「**並行バグの中で最も検出困難だった一族(データ競合=再現不能・環境依存・破壊的)が消え、残った並行バグは決定的で推論可能なもの(デッドロック等)だけになる**」です。「たまにしか起きない、ログにも残らない、本番でだけ起きる」あの悪夢の消滅——これだけでも、多くの組織にとってRust採用の十分な動機になっています。

# 第9章 深掘り:内部実装とunsafe

ここまでの章は「規則に従う」話でした。本章は「規則がなぜそう定義され、どう実装されているか」を扱います。規則の暗記から原理の理解へ——シニアエンジニアの学び方に最も合う章です。

## 9.1 Dropの詳細

### ドロップ順序の完全な規則

- **ローカル変数**:宣言と**逆順**(後入れ先出し)。後から作られた値は先の値への参照を持ちうるため、依存される側を後に壊す自然な順序です
- **構造体のフィールド**:宣言と**同順**
- **`Vec`等のコレクション要素**:先頭から順

```rust
struct Noisy(&'static str);
impl Drop for Noisy {
    fn drop(&mut self) { println!("drop {}", self.0); }
}

fn main() {
    let _a = Noisy("a");
    let _b = Noisy("b");
}
// 出力: drop b → drop a(宣言の逆順)
```

### drop flag —— 「ムーブされたかもしれない」の追跡

条件分岐によって「ムーブされたかどうかが実行時にしか分からない」値はどうなるでしょうか。

```rust
let s = String::from("hello");
if condition {
    consume(s);       // こちらの分岐ではムーブされる
}
// ここでsを解放すべきか否かは、conditionに依存する
```

コンパイラはこの場合に限り、**drop flag**という隠しビットをスタックに置き、ムーブ時にクリア、スコープ末尾でフラグを見て条件付きdropを行います。静的に決定できる大多数のケースではフラグは生成されず、ゼロコストが保たれます。「原則は静的決定、決定不能な場合のみ最小の実行時コスト」というRustの設計思想の好例です。

なお`std::mem::forget(v)`はdropを走らせずに値を忘れる関数で、safeです(1.3で述べた「リークは安全性違反ではない」の具体化)。FFIでリソースの管轄を他言語に引き渡す場面などで使われます。

### Dropと借用チェッカの相互作用

4.4で触れた通り、`Drop`実装を持つ型はNLLの「最後の使用で借用終了」の恩恵を受けにくく、スコープ末尾まで生きます。dropは副作用(ロック解放、flush等)を持つため、その実行位置を勝手に前倒しできないからです。ロックガードによる借用エラーの正体はこれです。

## 9.2 メモリレイアウト

### サイズとアラインメント

```rust
use std::mem::{size_of, align_of};

struct A { a: u8, b: u32, c: u16 }
println!("{}", size_of::<A>());   // 8 (12ではない!)
```

Rustのデフォルト表現(`repr(Rust)`)では、コンパイラは**フィールドを自由に並べ替えて**パディングを最小化します(この例では`b(4), c(2), a(1), pad(1)`)。C言語やJavaの直感(宣言順に並ぶ)と異なる点で、FFIでCと構造体を共有する場合は`#[repr(C)]`で宣言順レイアウトを強制します。

### ニッチ最適化 —— `Option<Box<T>>`がポインタ1個分である理由

Rustで最も美しい最適化の一つを紹介します。

```rust
println!("{}", size_of::<Box<i32>>());          // 8
println!("{}", size_of::<Option<Box<i32>>>());  // 8 (!!)
println!("{}", size_of::<Option<i32>>());       // 8 (i32の4 + タグ+パディング)
```

`Option<T>`は本来「タグ(Some/None)+中身」の領域が要るはずです。しかし`Box<T>`や`&T`は**絶対にnullにならない**(第4章)ことを型システムが知っています。ならば、ポインタのビットパターンのうち0(null)は**未使用**——この「使われない値の隙間(niche)」を`None`の表現に流用すれば、タグは不要になります。

これが意味するのは、**`Option<&T>`はCのnullableポインタと完全に同一のメモリ表現でありながら、null検査を型で強制する**ということです。「nullの安全性を取ると実行コストがかかる」というトレードオフが、ここでは存在しません。`NonZeroU32`など、niche を持つ型全般で同じ最適化が働きます。

### 参照の実サイズ(再訪)

| 参照の型 | 実体 | サイズ(64bit) |
|---|---|---|
| `&i32`, `&struct` | 単純ポインタ | 8 |
| `&str`, `&[T]` | ポインタ+長さ | 16 |
| `&dyn Trait` | ポインタ+vtableポインタ | 16 |

`&dyn Trait`のvtable方式はJavaの仮想メソッドテーブルと同じ発想ですが、置き場所が違います。Javaは**オブジェクト側**がクラスポインタを持ち(全インスタンスがヘッダを持つ理由の一つ)、Rustは**参照側**が持ちます。だからRustの構造体自体にはヘッダが無く(2.2)、動的ディスパッチのコストは`dyn`を使う箇所だけが払うのです。

## 9.3 借用チェッカの仕組み

借用チェッカは魔法ではなく、コンパイラパイプラインの一段です。全体像:

```text
ソースコード → HIR(高級IR) → MIR(中級IR) → LLVM IR → 機械語
                                  ↑
                        借用チェックはここで実行
```

MIR(Mid-level IR)は、ソースコードを基本ブロックと制御フローグラフ(CFG)に落とした表現です。借用チェッカはこのCFG上で、

1. 各変数の**生存区間**(liveness)をデータフロー解析で求める
2. 各借用の**リージョン**(借用が有効であるべきプログラム地点の集合)を制約として集める
3. 制約を解き、「借用が生きている地点で、衝突する操作(再借用・ムーブ・drop)が起きないか」を検査する

NLL(4.4)の正体は、この解析の単位が「レキシカルスコープ」から「CFG上の地点集合」へ精密化されたことです。だから「使用が終わった地点」で借用を終えられるのです。

現在も進化は続いており、次世代アルゴリズム**Polonius**は、借用の追跡を「どの地点で何が借用中か」から「各参照がどの元データ(origin)から来たか」という向きに再定式化し、現行チェッカが誤って拒否する一部の健全なパターン(条件分岐で参照を返す場合など)を受理できるようにする取り組みです。**借用チェッカが拒否するコードの中には、本当は安全なものも含まれる**(健全性のために保守側に倒している)——この事実を知っておくと、チェッカと戦うときの心持ちが変わります。「これは俺が間違っているのか、チェッカが保守的なだけか」を切り分け、後者なら素直に構造を変えればよいのです。

## 9.4 `unsafe`と生ポインタ

### unsafeは「検査の無効化」ではない

`unsafe`ブロックについての最大の誤解を最初に潰します。**unsafeブロック内でも、借用チェッカも型検査も全て動き続けます。** 解禁されるのは次の5つの操作だけです。

1. 生ポインタ(`*const T`, `*mut T`)の**参照外し**
2. `unsafe fn`の呼び出し(FFI含む)
3. 可変static変数へのアクセス
4. `unsafe trait`の実装
5. unionのフィールドアクセス

つまり`unsafe`とは「コンパイラが証明できない安全性条件を、**ここは私が証明済みである**と人間が引き受ける」という責任移転の宣言です。

```rust
let x = 42;
let p = &x as *const i32;    // 生ポインタを作るのはsafe
unsafe {
    println!("{}", *p);      // 参照外しにはunsafeが必要
}
```

生ポインタは借用規則もライフタイムも課されない、C言語のポインタ相当の存在です。だからこそ参照外しは「pが有効なメモリを指している」ことを人間が保証しなければなりません。

### 健全性(soundness)という契約

エコシステムの規律として重要なのは**「safeな公開APIは、どんな呼び方をされても未定義動作を起こしてはならない」**という健全性の契約です。ライブラリ内部で`unsafe`を使うのは正当ですが(後述の`Vec`のように)、その事実は利用者に漏れてはならず、悪意ある呼び出し順でもUBに至らないよう内部で不変条件を守り切る責任を負います。この契約があるからこそ、利用者は`unsafe`の存在を意識せずにsafe Rustの保証を信頼できます。実務指針として、

- アプリケーションコードで`unsafe`が必要になる場面はほぼ無い(FFIが主な例外)
- 使う場合は最小範囲で囲い、直前に「なぜ安全か」を`// SAFETY:`コメントで証明する(コミュニティ標準の慣習)
- Miri(未定義動作の実行時検出器)でテストを走らせる

## 9.5 標準ライブラリのコードリーディング —— `Vec`は「unsafeの上のsafe抽象」

総仕上げとして、ここまでの全概念が合流する場所——`Vec<T>`の内部を読みます(要旨に簡略化しています。実物は`rust-lang/rust`リポジトリの`library/alloc/src/vec/mod.rs`)。

```rust
pub struct Vec<T> {
    buf: RawVec<T>,     // 内部は生ポインタ+容量: ptr: NonNull<T>, cap: usize
    len: usize,
}

impl<T> Vec<T> {
    pub fn push(&mut self, value: T) {
        if self.len == self.buf.cap() {
            self.buf.grow();                       // 容量拡張(再確保+コピー)
        }
        unsafe {
            let end = self.as_mut_ptr().add(self.len);
            ptr::write(end, value);                // 生ポインタ経由で書き込み
        }
        self.len += 1;
    }
}
```

読み取るべき構造は3層です。

1. **最下層は生ポインタとunsafe**:アロケータから貰った生メモリの管理は、原理的にコンパイラには証明できない(「lenまでは初期化済み」という不変条件は人間の知識)。だからここは人間が健全性を証明する領域です。
2. **中間層で不変条件を守り切る**:「`0..len`の範囲は常に有効な`T`で初期化されている」「`len <= cap`」——`Vec`の全メソッドはこの不変条件を維持するよう書かれています。
3. **最上層はsafeなAPI**:利用者から見える`push`/`pop`/`get`は完全にsafeで、借用規則とライフタイムの保護下にあります。第4章のイテレータ無効化の検出も、`Vec`自体に特別な仕掛けがあるのではなく、「`iter()`が`&self`を借用する」という**普通のシグネチャ**から借用チェッカが導いた帰結です。

この「unsafeなコアを、safeな抽象で包み、不変条件で接着する」構造は、`Rc`(カウンタ操作)、`Mutex`(OSプリミティブ)、`String`(UTF-8不変条件)など標準ライブラリ全体を貫くアーキテクチャです。**Rustの安全性とは「unsafeが存在しないこと」ではなく「unsafeが検証可能な小さな領域に閉じ込められていること」**——この理解に到達すれば、本章の目的は達成です。

読み進める際の地図として:

| 読みたいもの | 場所(rust-lang/rustリポジトリ内) | 学べること |
|---|---|---|
| `Vec`, `String` | `library/alloc/src/` | unsafe上のsafe抽象、容量管理 |
| `Rc`, `Arc` | `library/alloc/src/rc.rs`, `sync.rs` | 参照カウントとDropの連携、Weakの実装 |
| `Cell`, `RefCell` | `library/core/src/cell.rs` | 内部可変性の最小実装(意外なほど短い) |
| `Mutex` | `library/std/src/sync/` | OSプリミティブのRAIIラッピング |

# 第10章 トラブルシューティング:エラー別対処索引

本章は「困ったときに引く」章です。10.1はエラーコード順の索引、10.2はコードレビュー観点のアンチパターン集、10.3は個別対処を超えた設計転換の話です。いずれも `rustc --explain E0xxx` と併用してください。

## 10.1 主要エラーコード別の対処法

### E0382: borrow of moved value / use of moved value

**症状**:ムーブ済みの変数を使った。

```rust
let s = String::from("hi");
let t = s;
println!("{s}");        // E0382
```

**対処の優先順位**:

1. **借用で済むならムーブしない**:`let t = &s;` あるいは関数側を`&T`引数に変える(最頻・最善)
2. **順序を変える**:使い終わってからムーブする
3. **複製する**:`let t = s.clone();`(コスト明示の上で)
4. **Copyをderiveする**:自作の小さな純データ型なら`#[derive(Clone, Copy)]`

**頻出の変種**:ループ内でのムーブ(`for`の各周回でムーブしようとして2周目に死ぬ)。ループ内で消費が必要なら、対象を`clone`するか、`Option::take`やコレクションの`drain`で「取り出し」を明示します。

### E0499: cannot borrow `x` as mutable more than once

**症状**:`&mut`を同時に2つ作った。

```rust
let a = &mut v;
let b = &mut v;      // E0499
a.push(1);
```

**対処**:

1. **借用の生存区間を分離する**:1つ目の使用を終えてから2つ目を作る(NLLにより、間に使用が挟まらなければ通る)
2. **1つの`&mut`を使い回す**:関数に渡すときは再借用(`&mut *a`)が自動で効くので、実は同じ`&mut`を連続で使うのは問題ない
3. **コレクションの2要素を同時に`&mut`したい場合**:`split_at_mut`, `iter_mut`, または`std::mem::swap`を使う(インデックス2つでの直接借用はチェッカが見分けられない)

### E0502: cannot borrow as mutable because it is also borrowed as immutable

**症状**:`&`が生きている間に`&mut`を作った(逆も同コード)。4.2のイテレーション中変更が代表例。

**対処**:

1. **読みの結果を値として確定させ、借用を先に終わらせる**:

```rust
let first = v[0];              // before: let first = &v[0]; (借用が残る)
v.push(first * 2);             // after: firstはCopyされた値なので借用なし
```

2. **フェーズを分ける**:「走査して変更対象を集める(読み)→まとめて変更する(書き)」の2パスに分割。`retain`, `drain`, `extend`などの専用APIが1パスで安全にやってくれることも多い

### E0505: cannot move out of `x` because it is borrowed

**症状**:借用が生きているのに本体をムーブした。**対処**:E0502と同型。借用の使用を終えてからムーブする。

### E0507: cannot move out of borrowed content / out of index

**症状**:借用越しに中身の所有権を奪おうとした(`&self`のメソッドでフィールドをreturnする、`v[0]`で非Copy値を取り出す等)。

**対処**:

1. 参照を返す:`&self.name`(+必要ならライフタイム)
2. 複製して返す:`self.name.clone()`
3. 所有権ごと取り出すAPIを使う:`v.remove(0)`, `v.swap_remove(0)`, `option.take()`, `std::mem::take(&mut self.name)`(デフォルト値と交換して奪う——「抜け殻を残して持ち去る」定石)

### E0597: `x` does not live long enough / E0716: temporary value dropped while borrowed

**症状**:参照が値より長生きしようとした。E0716は特に「一時値への参照」で頻出:

```rust
let r = &make_string();     // E0716: 式の一時値は文末で死ぬのに参照が残る
```

**対処**:

1. **値に名前を与えて寿命を確保する**:`let s = make_string(); let r = &s;`
2. **値の宣言をより外側のスコープへ移す**
3. **参照でなく所有で持つ/返す**:構造体フィールドや戻り値なら`String`にする(5.3パターンC)

### E0106: missing lifetime specifier

**症状**:省略規則(5.2)で決まらないシグネチャを書いた。

**対処**:戻り値の参照が**どの引数由来か**を考えて注釈する(5.3)。どの引数由来でもない(関数内で作った値への参照)なら、それは設計エラーであり、所有された値を返すしかありません。

### E0277: `Rc<...>` cannot be sent between threads safely

**症状**:非Sendな型をスレッド境界に持ち込んだ(8.1)。

**対処**:`Rc`→`Arc`、`RefCell`→`Mutex`/`RwLock`に置換。エラーメッセージの`required because...`の連鎖を下から読むと、「構造体の奥のどのフィールドが原因か」を特定できます。

### 番外:closure may outlive the current function (E0373)

**症状**:スレッドや長寿命コールバックにクロージャを渡すとき、借用キャプチャが寿命を超えた。**対処**:ほぼ常に`move`を付けて所有権ごとキャプチャ(8.2)。元の変数も使い続けたいなら、渡す前に`clone`してcloneのほうをmoveする。

## 10.2 アンチパターン集 —— レビューで指摘される前に

**AP1: 反射的clone(clone-driven development)**
症状:借用エラーの度に`.clone()`。第7章7.3の卒業ロードマップ参照。レビュー観点:「このcloneは設計上の必要か、コンパイラ対策か?」をコメントで問う。

**AP2: `Rc<RefCell<T>>`の無秩序増殖**
症状:構造体のフィールドが軒並み`Rc<RefCell<...>>`。原因はJava流「みんなが参照を持ち合う」オブジェクトグラフの直訳(6.5)。実行時パニック(`BorrowMutError`)の温床になり、Rustの静的保証を自ら放棄している状態。→10.3で設計転換。

**AP3: ライフタイム注釈での力業**
症状:エラーが消えるまで`'a`, `'b`を書き足し、`struct App<'a, 'b, 'c>`のような型が誕生する。5.6の通り、注釈は寿命を変えられないので、これは問題の先送りです。参照フィールドを所有(`String`等)に替えるほうが、わずかなメモリと引き換えに設計全体が単純になります。**構造体のライフタイクパラメータが2個を超えたら設計を疑う**のが経験則です。

**AP4: `unsafe`への安易な逃避**
症状:借用エラーを生ポインタで迂回する。borrow checkerが拒否したコードの多くは本当に危険であり、unsafeで黙らせたものは高確率で未定義動作です(9.4の健全性契約違反)。unsafeは「チェッカより賢い人間が証明を引き受ける」ための道具であって、「チェッカに負けた人間の脱出口」ではありません。

**AP5: 長寿命構造体への参照フィールド**
症状:`struct Server<'a> { config: &'a Config }`のような設計(5.4)。アプリのルート付近の構造体にライフタイムが付くと、そのパラメータがアプリ全体に伝播します。長寿命オブジェクトは所有(または`Arc`)で持つ。参照フィールドは短命なビュー型(パーサ等)に限定する。

**AP6: getterで所有権を返す**
症状:`fn name(self) -> String`(selfを消費)や、毎回`clone`して返すgetter。基本は`fn name(&self) -> &str`で借用を返し、複製は呼び出し側に委ねます(コスト決定権を利用者へ)。

**AP7: インデックスアクセスによる二重可変借用回避の失敗**
症状:`let a = &mut v[i]; let b = &mut v[j];`(E0499)。チェッカは`i != j`を証明できません。→`split_at_mut`、または処理を`v.iter_mut()`のパイプラインに再構成。

## 10.3 borrow checkerと「戦わない」設計への転換

個別エラーを潰す段階の先に、「そもそもエラーが出ない形にデータを持つ」段階があります。中級への壁を越える3つの転換を紹介します。

### 転換1: 参照のグラフを、IDによる間接参照に変える

Javaで自然だった「オブジェクトがオブジェクトを直接参照し合うグラフ」は、Rustでは`Rc<RefCell>`地獄への入口です。定石は**アリーナパターン**:実体は1つの所有者(Vec等)に集め、相互関係はインデックス/IDで表現します。

```rust
// Java流の直訳(苦しい)
struct Employee { manager: Option<Rc<RefCell<Employee>>>, /* ... */ }

// アリーナ+ID(Rustらしい)
struct EmployeeId(usize);
struct Company {
    employees: Vec<Employee>,          // 所有者はCompany唯一
}
struct Employee {
    manager: Option<EmployeeId>,       // 関係はただの数値
}
```

借用は`&company.employees[id.0]`のように**使う瞬間だけ**発生し、保持されません。ライフタイムは消え、循環参照も定義上不可能になり、シリアライズまで簡単になります。ゲームエンジン(ECS)、コンパイラ(ASTのノードID)、グラフライブラリ(petgraph)がみなこの形なのは偶然ではありません。

### 転換2: 「更新しながら読む」を「読み切ってから更新する」に分ける

E0502系の多くは、1つのループに読みと書きを詰め込んだことが原因です。関数型スタイルへの再構成——「入力を読んで変更計画(新しい値、削除対象リスト等)を作る純粋なフェーズ」+「計画を適用する可変フェーズ」——に分けると、借用の衝突は構造的に消えます。イミュータブルデータ設計に馴染みのある読者なら、これはむしろ得意分野のはずです。

### 転換3: 所有の階層を先に決めてからコードを書く

Javaでは「クラス間の関連」から設計を始められましたが、Rustでは**「このデータの唯一の持ち主は誰か」**を最初に決めるのが近道です。所有関係が木を成すように配置し(7.5)、横断アクセスは「一時的な借用を関数引数で渡す」で賄う。この順序で設計されたコードは、借用チェッカとほとんど衝突しません。**チェッカとの戦いが激しいのは、コードが悪いのではなく、所有権が未設計であるサイン**——このメタ認知こそが、本章で持ち帰ってほしい最大の教訓です。

## 11.3 借用規則・ライフタイム省略規則の要約

**借用規則**

1. 任意の時点で、ある値に対して有効なのは「複数の`&T`」または「1つの`&mut T`」のどちらか一方(共有XOR可変)
2. 参照は、参照先の値より長生きできない
3. 借用の終端は「最後に使用された地点」(NLL)。ただし`Drop`実装型はスコープ末尾まで
4. `&mut`が有効な間は、所有者自身も値に触れない

**ライフタイム省略規則(関数シグネチャ)**

1. 引数の各参照に、個別のライフタイムパラメータを割り当てる
2. 入力ライフタイムがちょうど1つなら、それを全出力に適用
3. `&self` / `&mut self`があれば、selfのライフタイムを全出力に適用
4. どれも当てはまらなければ、明示注釈が必要(E0106)

**変数の挙動まとめ**

| 書き方 | 再代入 | 値の変更 | 型変更 |
|---|---|---|---|
| `let x = v;` | ✗ | ✗ | — |
| `let mut x = v;` | ✓ | ✓ | ✗ |
| `let x = v;`(シャドーイング) | (新束縛) | (新束縛) | ✓ |
